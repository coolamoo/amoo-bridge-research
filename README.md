# AMOO Bridge Research · 手机自动化桥接研究

这份仓库记录「用无障碍桥在 Android 手机上驱动第三方 App 完成任务」的实测结论，
以高德地图（`com.autonavi.minimap`）的达人日常任务为第一条落地链路。

重点是**可复现**：每一步都写清楚命令长什么样、坐标怎么来的、失败长什么样。

## 为什么有这套东西

手机上大量任务（每日签到、答题、游戏、领券）没有公开 API，只能靠 UI 操作。
直接上 OCR 或纯坐标点按都不稳，实测下来最可靠的是三层组合：

1. **控件树**（AccessibilityService）负责「有名字的东西」——按钮、tab、列表文字；
2. **截图 + 视觉**负责「没名字的东西」——H5 画布、游戏界面、图表；
3. **文件队列协议**负责「怎么把命令递进去」——不依赖 HTTP 端口、不依赖 adb。

三者缺一不可，只用其中一层都会卡住。

## 三条最贵的经验

1. **控件树坐标 ≠ 触控坐标。** 在高德半屏页面上，树里给的 y 比真实按钮低约 570 px，
   按树坐标点下去毫无反应。必须用截图量。
2. **OCR 救不了 H5 和游戏画面。** 同一个引擎在原生列表页能读，在游戏画布上只能吐乱码，
   `zoom` 参数不生效。别在那里烧调用次数。
3. **连续操作必须打包成一条链。** 只要中间向外输出一句话，前台就被聊天界面抢走，
   后续所有点击都打在聊天窗口上。

## 适用范围

- 设备：Android 手机，屏幕 1200×2670
- 桥：AMOO 桥 Pro（`com.stepclaw.bridge`），早期验证版为 桥导航（`com.amoo.bridge`）
- 目标 App：高德地图 `com.autonavi.minimap`

换设备要重测坐标；换 App 要重走一遍「找入口 → 量坐标 → 验证反馈」。
